# 流式语音架构（v3）

2026-11-19 起，本仓库的交付模型从「一次请求一份完整 WAV」改成**句子级流式**。旧的整段接口保留为兼容壳，不再是主路径。

## 一句话

一条气泡进来，先切成句子；首句立刻合成、立刻交付；后面的句子在播放第一句时继续合成；每一段都是完整 WAV，播放端按序接上。

## 链路

```
Cortico/Coo 气泡（desktop-pet.self, kind=say/ask）
  → cortico-world-tts-stream（本仓库 coo/）每 200 ms 扫一次事件库
  → POST {gateway}/v1/audio/segments
       ├ 切句（强句末必切；弱停顿够长才切；首句≤11 字早切，且避开紧随其后的标点）
       ├ 第 1 段：4 步 CFM、语速 1.067、streaming_mode=3
       ├ 第 2..n 段：16 步、语速 0.97、streaming_mode=2
       ├ 每段：上游流式收齐 → 按「第一个有声帧（10 ms / -45 dBFS）+ 50 ms 预滚」裁前导静音
       │        → 段首 8 ms 淡入、段尾 15 ms 淡出 → 重新封装成标准 WAV
       └ 以「4B 长度 + 1B 类型 + 载荷」分帧输出：类型 0 JSON 元数据，类型 1 该段 WAV
  → World 每收到一段：落盘 → 送 player.ps1（SoundPlayer 串行播放）
  → 同时可继续转发给 MicroDuck（未接线，见「未完成」）
```

## 为什么不学「整段先合完」

GPT-SoVITS 的合成耗时大致与字数成正比（P104 / v2Pro 实测 RTF 0.36–0.55）。一条 40 字的气泡整段合成要 2–4 秒，人在这段时间里听不到任何东西。切句之后，第一段只有 1–2 秒音频，0.5–0.9 秒就能合成完。

## 关键决策

| 决策 | 理由 |
| --- | --- |
| 切句放在网关，不放在客户端 | 客户端只负责播放；换客户端不用重写切句。 |
| 首句单独一套参数 | 4 步 CFM 与更快语速能省掉第一段的固定开销；后续段回到 16 步保音质。 |
| 首句至少 5 个字才在弱停顿处切 | 3 个字的「你好，」只有 0.5 秒音频，盖不住第二段的合成时间，会听到空档。 |
| 早切前先看 6 个字符 | 免得把「……再说。」从中间劈开，也免得切开 `3.14`、`file.txt`。 |
| 段失败补 40 ms 静音占位 | 播放端按序号接续；缺一段就永远停在那里。静音占位是活性保障，不是审美。 |
| 不用 `wave` 模块读上游流式 WAV | 上游把 `data` 块长度写成 0，`wave` 会读出 0 帧。自己走 chunk 表，取到字节流末尾。 |
| 播放器用 SoundPlayer 而不是 MediaPlayer | 同步播放、无消息循环依赖；MediaPlayer 适合单文件、不适合排队。 |

## 实测（2026-11-19）

| 指标 | 值 | 出处 |
| --- | --- | --- |
| GPU 热机首字节 | 0.36–0.83 s | `docs/measurements-2026-11-19.md` |
| CPU 首字节 | 2.1–4.0 s | 同上（同一权重，仅 device 不同） |
| 端到端首段到播放器 | 0.77–1.27 s | `coo/tools/stream-smoke.mjs` |
| 4 段连续、无空档 | 是 | 同上（第三段到达时第二段还在播） |
| 合成 RTF | 0.36–0.55 | 同上 |

前提：上游必须是 **GPU** 实例。`E:\GPT-SoVITS\...\GPT_SoVITS\configs\tts_infer.yaml` 的 `custom.device` 要是 `cuda`；曾经有一段时间现场跑的是临时 CPU 配置，那是性能陷阱。

## 兼容

- `POST /v1/audio/speech`：OpenAI 语义，仍返回整段 WAV。Coo 的 market `tts` 插件、DSH 插件都还走这里。
- `POST /v1/audio/segments`：本仓库的主路径，帧流。

## 未完成

1. MicroDuck 转发：World 目前只在本机播放。鸭身要有声，需要再加一个订阅者（或让 World 把每段 WAV 经 SSH 送到板上 aplay）。
2. 打断：新气泡会顶掉旧的一轮合成，但已经在播的那一段会念完（SoundPlayer 不支持中途停）。
3. 首句音频缓存：还没做。Amadeus 用内容寻址缓存首句，命中时能再省 0.5 秒。
4. 自适应聚合：现在每句一请求；句子很碎时请求开销占比会上升，后续可按「播放余量」合并后句。
